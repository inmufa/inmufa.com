Permissions should be a row, not a deploy

Lapka is a pet-supplies marketplace that lives inside Telegram. Shops run their own catalogue, orders and payments from a web dashboard. In the first version, access control was what most backends start with: an is_owner boolean and a handful of if request.user.role == "manager" checks scattered through the views. It worked, until a shop owner asked for a staff account that could see orders but not touch payouts.

Where the hard-coded version breaks

That request isn't exotic, it's the first thing every real shop asks for once it has more than one person working it. With roles as code, answering it means adding a new branch to every view that cares about permissions, shipping a deploy, and hoping the next role request doesn't need a slightly different combination that doesn't fit the branches you already wrote. Every shop's actual staffing situation is slightly different, and code can't model "slightly different" without either exploding into special cases or forcing everyone into the same three roles.

What a data-driven version looks like

I replaced the role checks with a permissions table: a set of named capabilities (orders.view, payouts.manage, catalogue.edit, and so on) and a join table mapping staff accounts to the capabilities they hold. A view doesn't ask "is this user a manager," it asks "does this user hold payouts.manage." The owner account is seeded with every capability and that row is protected from being edited away, so there's always at least one account that can't accidentally lock itself out.

Creating a new staff role, from the shop owner's side, is filling in a form that ticks the capabilities they want and saving it. From my side, it's a migration that ran once, months ago, and never needs to run again for this. The admin dashboard, the bot, and the API all check the same table, so there's exactly one place permissions logic can be wrong, not three that can quietly drift apart.

The part worth remembering

The win isn't "database over if-statements" as a rule, that's not universally true. It's recognising which parts of a system's behaviour belong to the business, not to the code, before the business asks for the first exception you didn't design for. Permissions are almost always one of those parts. Treating them as data from day one costs very little up front and removes an entire category of future deploys.
