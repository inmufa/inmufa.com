Designing the API before the team exists

Kigo is a booking and tournament ecosystem with a merchant panel, a coach marketplace, bar POS, subscriptions, and three separate tournament systems. When I joined, it was one backend developer: me. The team that exists now - more backend engineers, a frontend team, three Telegram bots each with their own integration surface - didn't exist yet. I designed the API as if it already did.

What that meant in practice

Before writing a view, I wrote the OpenAPI spec for that resource: the shape of the request, every response code it could realistically return, and the error envelope. Not a sketch, the actual spec, versioned in the repo next to the code. Only after that got reviewed did implementation start. It felt slower in week one. By month three, when the first additional backend engineer joined, they opened the spec, not the codebase, and started shipping endpoints against a contract that was already agreed on, without a single meeting about "how should this work."

The domain model got the same treatment before it got code. A coach marketplace with wallets and payouts, three different tournament formats, and a merchant panel sound like separate products. Modelled carelessly, they are three separate products wired together with duct tape. Modelled as one domain first - clubs, memberships, bookings, settlements, as entities that each system reads and writes the same way - a club owner's dashboard, a tournament bracket, and a coach's payout history all sit on the same four tables instead of three incompatible ones.

The part that's easy to get wrong

None of this is "write more documentation." A spec nobody enforces rots in a week. What makes it work is that the spec is the thing pull requests get reviewed against: if an endpoint's behaviour doesn't match what's published, that's the bug, not the spec. CI checks the implementation against the schema on every PR. That single rule is what turns a document into a contract people actually trust enough to build against without re-reading the handler.

Why this mattered more than the tech stack

Django, DRF, Celery, Channels - all of that is replaceable, and parts of it have been replaced since. The thing that didn't change, and that let the platform grow from one engineer to a team without a rewrite, was that the API's shape was decided on purpose, in writing, before the convenience of "I'll just add a field" could decide it by accident.
