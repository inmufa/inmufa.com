Why I stopped trusting an ORM with money

e-expert prices real estate, vehicles and specialised machinery for banks that use the number to decide how much to lend against it. That number has to be the same number every time you ask for it, on every machine, for the life of the loan. Once I understood that requirement properly, I stopped writing valuation math the way Django makes it easy to write it.

The bug that taught me this

Early on, a comparative valuation came back with a different result on a re-run of the same inputs, off by a few hundred som. Nothing in the business logic had changed. The culprit was a chain of DecimalField values getting coerced to Python float somewhere in a third-party scoring library, then back to Decimal for storage. Floats don't round-trip cleanly through that kind of chain. Each hop introduced a few bits of drift, and with enough comparables in the average, the drift was visible in the final price.

The ORM wasn't wrong. It stores and fetches exactly what you tell it to. The problem is that it's very easy to write code that looks like it's working with exact decimal arithmetic the whole way through when it isn't, because nothing in the type system stops a float from sneaking into the middle of the chain.

What changed

I moved every money-adjacent calculation into a small set of pure functions that only accept Decimal and raise on anything else, no implicit casting anywhere near them. The ORM still does what it's good at: fetching rows, expressing relationships, handling migrations. It no longer touches a single multiplication involving a price. If a value needs to leave that boundary for a third-party library that only speaks float, it gets converted explicitly, logged, and never converted back - the result of that step is treated as an estimate, not a stored price.

I also added a property-based test that generates thousands of random comparable sets and asserts the valuation function is deterministic: same input, byte-identical output, every time, no matter the order the comparables arrive in. That test has caught two regressions since, both from well-meaning refactors that looked completely safe in review.

The actual lesson

An ORM is a tool for modelling your schema, not your arithmetic. The moment a calculation feeds into a number someone else's money depends on, it deserves its own boundary, its own types, and its own test that doesn't trust "it compiled" as evidence of correctness. That boundary is maybe two hundred lines of code in a service with tens of thousands. It's also the only part of it a cybersecurity review and a bank's own auditors ever asked to see twice.
